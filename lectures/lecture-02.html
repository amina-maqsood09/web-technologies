Tiered Web Architecture

How a web system splits its work into one-tier, two-tier and three-tier designs, and how to choose between them.

What you will learn

  • What separation of concerns means.
  • The difference between a tier and a layer.
  • How one-tier, two-tier and three-tier (N-tier) systems work.
  • How to compare architectures by scalability, maintainability and cost.

Key idea: separate responsibilities so a change in one part does not unnecessarily break the others.

Lecture content

Tiers vs. layers

These ideas are related, but not identical.

Tier

Physical or deployment separation. It tells you where components run: the same machine, a client and a server, or several servers.

Layer

Logical responsibility. It tells you how the software is organized: presentation, business logic and data access.

One-tier architecture

A standalone application where the user interface, the logic and the data live together in one environment.

Examples

A desktop calculator, a local inventory tool, a single-machine utility.

Pros

Simple, with low deployment complexity.

Limitation

A poor fit for large, multi-user web systems.

Two-tier architecture

The client talks directly to a server and database. Requests go one way and responses come back.

Advantages

A simple mental model, easy for small systems, direct communication.

Limitation

Business logic and data access can become tightly coupled, and scaling can be harder.

Three-tier / N-tier architecture

The responsibilities are separated so each tier can grow independently.

1. Presentation

Browser and user interface.

2. Application

Business logic, API and services.

3. Data

Database and persistent storage.

This is the common web pattern: browser, then API or services, then database. Each tier can change or scale with less impact on the others.

Choosing an architecture

Every choice is a trade-off between three things.

Scalability

Can the system handle more users? This matters more as traffic grows.

Maintainability

Can a team change one part safely? This matters more as the codebase grows.

Cost

What infrastructure and operating effort can you afford? Balance now against later.

Rule of thumb

Start simple when that is appropriate. Separate concerns when complexity or scale justifies it.

Comparison

Aspect One-tier Two-tier Three / N-tier
Deployment One environment Client + server/data Separated components
Communication Mostly local Client to server Presentation, application, data
Separation Low Moderate Higher
Small or simple systems Often suitable Often suitable May add complexity
Large, multi-user web Poor fit Can become harder to scale Separates responsibilities

Practice

Decide first, then check the hint and the answer.

Challenge: name the architecture

Which architecture fits each system? (a) A desktop calculator. (b) A browser that talks to an API, which talks to a database. (c) A small client app that talks straight to a database server.

Show hint

Count how many separate parts exist, and whether anything sits between the client and the data.

Show answer

(a) One-tier, (b) three-tier, (c) two-tier.

Challenge: tier or layer?

Is each statement about a tier or a layer? (a) The web server and the database run on different machines. (b) The code is organized into presentation, business logic and data access.

Show hint

Tier is about where things run. Layer is about how responsibilities are organized.

Show answer

(a) Tier, because it describes physical or deployment separation. (b) Layer, because it describes logical responsibility.

Quick check

Answer in your head first, then open the answer.

1. What is the difference between a tier and a layer?

A tier is physical or deployment separation. A layer is logical separation of responsibilities.

2. Why is one-tier a poor fit for a large multi-user web system?

The interface, logic and data are tightly coupled in one environment, so it does not suit many users on the web.

3. Name the three tiers of a common web application.

Presentation (browser/UI), application (business logic/API) and data (database).

4. Which three trade-offs help you choose an architecture?

Scalability, maintainability and cost.

Tips and common mistakes

Common mistake

Using the words tier and layer as if they mean the same thing. One is about where it runs, the other is about how it is organized.

Common mistake

Assuming three-tier is always best. For a small, simple system it may only add complexity.

Pro tip

When you draw a system, label each box as presentation, application or data. If a box does two jobs, that is a sign to separate it.
